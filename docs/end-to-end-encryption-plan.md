# End-to-End Encryption Hardening Plan

QtNetworkChat currently treats the server as a transparent carrier for private-message E2E envelopes, identity announcements, and session rotation control messages. The client keeps the trust decision local: peer identity public keys are observed from online announcements, displayed as SHA-256 fingerprints, and verified with a short cross-device code before the default encrypted data plane is allowed. Authenticated session setup now requires identity-signed request/response transcripts and derives local session keys without sending the raw session key over the wire. Redis-backed multi-instance deployments also route E2E identity announcements and signed rotation control messages as small control-plane events; session keys, private identity material, and full file ciphertext are still not cached in Redis.

## Current Authenticated Agreement Boundary

- The E2E cryptographic surface now has an explicit backend contract. CMake generates a sanitized `qtnetworkchat_e2e_crypto_config.h` with compiled backend id, requested production backend, production adapter id, production request/availability flags, adapter linked flag, required operation list, provider API header path, provider table ABI, required provider symbols, provider table binding flag, and reason strings. The public `qtnetworkchat_e2e_provider_api.h` fixes the future reviewed adapter's C ABI: table ABI, operation contract version, operation enum, material policy enum, input/output structs, operation function pointer, and eight-symbol provider table. Runtime status exposes `compiledBackendId`, `requestedBackendId`, `selectedBackendId`, `selectionSource`, `registeredBackends`, `selectedProviderReadiness`, `selectedProviderCompatibility`, `productionAdapterLinked`, `productionReady=false`, `productionRequiredOperations`, `available`, `productionRequired`, `unavailableReason`, and an operator action. The same status also publishes a sanitized per-operation matrix for session-key generation, identity-key generation, public-key derivation, agreement signing, signature verification, session derivation, payload encryption, and payload decryption; every public E2E primitive is gated through a shared adapter execution context and provider dispatch contract before draft material can be generated or consumed. Each operation reports its sanitized `providerId`, `operationContractVersion`, `dispatchState`, `providerSelfTestStatus`, `providerReadinessGate`, `providerCompatibilityStatus`, `providerCompatibilityGate`, `entrypoint`, `blockedReason`, and whether it requires production readiness. Production operation status now also carries an `operationImplementation` block for each required operation, including implementation state, vector set id, compatibility status, migration blocker, and operator action. Provider compatibility evidence now names the required operation contract, covered operations, known-answer vector set, known-answer/round-trip state, fail-closed proof, the production operation manifest, the production operation harness, the production operation execution plan, the production operation invocation contract, the reviewed operation slot registry, the dispatch binding table, the callable manifest, the sanitized execution result contract, and the provider table binding evidence without exposing raw keys or private material. Runtime status includes `productionOperationHarness` with schema `qtnetworkchat-e2e-production-operation-harness-v1`; it publishes one sanitized fixture hash per required operation and stays blocked until each reviewed operation is runnable. Runtime status also includes `productionOperationExecutionPlan` with schema `qtnetworkchat-e2e-production-operation-execution-plan-v1`; it orders the eight required production operations, ties every step to harness fixture evidence, and remains blocked until every step is harness-runnable. Runtime status also includes `productionOperationInvocation` with schema `qtnetworkchat-e2e-production-operation-invocation-v1`; it fixes each future reviewed operation's input/output contract, callable state, fixture hash, vector set, and material export proof, while keeping all current placeholder operations blocked. Runtime status also includes `productionOperationSlots` with schema `qtnetworkchat-e2e-production-operation-slots-v1`; it assigns stable slot ids, provider symbols, migration phases, review state, side-effect policy, and material policy to every required operation so a real adapter cannot become ready without reviewed callable slots. Runtime status also includes `productionOperationDispatchBindings` with schema `qtnetworkchat-e2e-production-operation-dispatch-bindings-v1`; it binds each slot to the expected provider symbol, ABI-style signature, input/output contract, fixture hash, and dispatchCallable state so a linked placeholder remains blocked until the reviewed provider table is actually bound. Runtime status now also includes `productionOperationCallableManifest` with schema `qtnetworkchat-e2e-production-operation-callable-manifest-v1`; it lists each required provider callable, ABI signature, fixture hash, material policy, and symbol/ABI/fixture match proof, while keeping linked placeholders non-callable. Runtime status now also includes `productionOperationExecutionResult` with schema `qtnetworkchat-e2e-production-operation-execution-result-v1`; it fixes the sanitized result contract for each future reviewed provider call, including output-contract proof, fixture proof, error class, and material-export proof, while proving current placeholders do not emit raw session keys, private identity material, or full public identity material. Runtime status now also includes `productionProviderTable` with schema `qtnetworkchat-e2e-production-provider-table-v1`; it records the provider API header path, provider table ABI, header ABI match, header operation count match, build probe reason, required provider symbols, bound/missing symbol counts, callable-manifest linkage, binding probe, registration gate, operation preflight gate, provider invocation dry-run gate, and per-symbol fixture/ABI proof, keeping not-linked and linked-placeholder adapters fail-closed. Runtime status also includes `productionProviderTableBindingProbe` with schema `qtnetworkchat-e2e-production-provider-table-binding-probe-v1`; it records sanitized struct sizes, provider table field offsets, function pointer slot size, operation enum to provider-symbol mapping, table binding status, runtime registration status, operation preflight status, and the non-executing structural table validator result. Runtime status also includes `productionProviderTableRegistration` with schema `qtnetworkchat-e2e-production-provider-table-registration-v1`; `e2eRegisterProductionProviderTable` records a runtime provider table pointer for evidence and validates it without invoking any crypto operation, while keeping `accepted=false` unless the build has a reviewed bound table and the provider is production-ready. Runtime status also includes `productionProviderOperationPreflight` with schema `qtnetworkchat-e2e-production-provider-operation-preflight-v1`; it checks every registered provider operation pointer, ABI signature, input/output contract, fixture hash, and material policy without invoking crypto. Runtime status also includes `productionProviderInvocationDryRun` with schema `qtnetworkchat-e2e-production-provider-invocation-dry-run-v1`; it builds sanitized per-operation invocation evidence and expected result state without calling any provider callback. `e2eValidateProductionProviderTable` validates a supplied provider table for ABI, sanitized provider id, operation count, and all eight function pointers without invoking any crypto operation. Runtime status also includes a `productionAcceptance` object with schema `qtnetworkchat-e2e-production-crypto-acceptance-v1`; it always evaluates the production adapter, not the current draft selection, and summarizes linked/readiness/compatibility/material-export/operation-dispatch/provider-table gates plus per-operation acceptance evidence. Until all required production operations are linked, reviewed, compatible, non-exporting, dispatchable, harness-runnable, execution-plan-ready, invocation-callable, slot-reviewed, dispatch-bound, callable-manifest accepted, execution-result accepted, provider-header-matched, provider-table-validated, provider-table-registered, provider-operation-preflight-passed, provider-invocation-dry-run-passed, provider-binding-probe-passed, and provider-table-bound, `accepted=false` and the release gate remains blocked. Identity and session status include this backend block without exposing raw session keys, private identity material, or full payloads.
- `QTNETWORKCHAT_E2E_ENABLE_PRODUCTION_CRYPTO=ON` plus `QTNETWORKCHAT_E2E_PRODUCTION_CRYPTO_BACKEND=openssl` is currently a CMake probe path only. It may detect OpenSSL for future adapter work, but it deliberately keeps `productionReady=false`, `productionBackendAvailableAtBuild=false`, and `productionProviderTable.tableBound=false` until the backend implementation is wired against `qtnetworkchat_e2e_provider_api.h` and covered by protocol compatibility tests. `QTNETWORKCHAT_E2E_LINK_PRODUCTION_ADAPTER=ON` now configures a linked placeholder adapter instead of a fatal configure stop; this exposes `productionAdapterRequested=true`, `productionAdapterLinked=true`, `productionAdapterReason=production-adapter-linked-placeholder`, and `productionProviderTable.buildProbeReason=production-provider-table-linked-placeholder` so CI can verify the runtime boundary while every operation still fails closed with `production-adapter-not-ready`.
- Runtime status now also includes `productionProviderCallFrame` with schema `qtnetworkchat-e2e-production-provider-call-frame-v1`. It fixes the sanitized C ABI call frame for each future provider callback, including operation enum value, suite id, primary/secondary/AAD input classes, max byte bounds, output material policy, input/output contract hashes, and explicit `operationInvoked=false`/`inputBytesAttached=false`/`outputBytesAttached=false` evidence for the current placeholder path. Runtime status also includes `productionProviderInvocationResult` with schema `qtnetworkchat-e2e-production-provider-invocation-result-v1`. It defines the sanitized result-capture contract for future reviewed provider calls, including status code class, output contract proof, fixture proof, error class, material export proof, and explicit `operationInvoked=false`/`resultCaptured=false` evidence for the current placeholder path. `productionAcceptance`, provider compatibility evidence, and production rotation dry-run/execute evidence remain blocked until provider preflight, provider call frame, invocation dry-run, invocation result capture, provider table registration, binding probe, and bound symbols all pass without sensitive material export.
- Operators can set `QTNETWORKCHAT_E2E_REQUIRE_PRODUCTION_CRYPTO=1` to fail closed when the current build has only the draft backend, or set `QTNETWORKCHAT_E2E_CRYPTO_BACKEND=production` / `openssl` to explicitly request the production adapter. If the placeholder is not linked, operations fail with `production-crypto-backend-unavailable`; if the placeholder is linked, operations fail with `production-adapter-not-ready`. Both paths block draft session-key generation, draft identity-key generation, agreement signing, signature verification, session derivation, payload encryption, payload decryption, and identity announcement before any draft encrypted data plane is used. Unknown backend ids are sanitized, every operation reports `unsupported-crypto-backend`, and there is no silent fallback to draft when a production adapter was requested.
- Local identity stores, trust pins, and in-memory sessions now carry backend migration evidence. Existing draft identity files remain inspectable under a production backend request, including their stored public-key fingerprint and `backendId=draft-qt-hmac-stream-v1`, but status marks `backendMigrationRequired=true`, disables agreement signing, and blocks identity announcements, encrypted sends, and rotation. Trust pins and sessions expose the same draft backend id plus blocked reason so operators can distinguish "adapter unavailable" from "stored draft material needs migration" without dumping private keys, raw session keys, or peer public keys.
- Migration recovery is explicit and evidence-backed for local draft E2E state. `planE2EBackendMigration` reports sanitized counts, affected peers, backend ids, blocked reasons, and short fingerprint summaries without private keys, raw session keys, peer public keys, local paths, or full fingerprints. `planE2EProductionRotationDryRun` adds a non-destructive production rotation readiness view over the same local state: it reports provider readiness/compatibility gates, affected peer pins and sessions, and whether in-place rotation can proceed, while proving it will not clear identity stores, trust pins, active sessions, or pending agreements. Until the provider is production-ready, the dry-run release gate remains `production-crypto-provider-not-ready`. The same dry-run and `executeE2EProductionRotation` evidence now include the shared `productionAcceptance` gate, `productionOperationExecutionPlan`, `productionOperationInvocation`, `productionOperationSlots`, `productionOperationDispatchBindings`, `productionOperationExecutionResult`, `productionProviderTableRegistration`, `productionProviderOperationPreflight`, `productionProviderInvocationDryRun`, and a seven-stage rotation manifest for production identity generation, public derivation, agreement sign/verify, session derivation, payload encrypt, and payload decrypt, with each stage tied to the selected provider operation matrix and compatibility gate. `executeE2EProductionRotation` is present as the reviewed-production execution entrypoint, but today it only records sanitized fail-closed evidence and refuses to mutate local state until `canRotateInPlace=true`, production acceptance is satisfied, the execution plan is ready, every invocation contract is callable, every production slot is reviewed, every dispatch binding is callable, every sanitized execution result has passed, the provider operation preflight and invocation dry-run have passed, and the provider table is registered and bound; this prevents a future production toggle from accidentally reusing draft identities or sessions. `executeE2EBackendMigration` records before/after migration evidence, removes the local identity store and trust-pin store, clears active sessions and pending agreements, and leaves observed peer identities as unverified public observations. `clearE2EBackendMigrationState` remains as the compatibility wrapper used by the contact menu. After execution the client must receive fresh identity announcements, re-check verification codes, and derive a new session before encrypted private text or files can resume.
- `E2EKeyAgreement` now carries both `senderIdentityFingerprintSha256` and `receiverIdentityFingerprintSha256` in addition to the rotation public key fingerprint and a draft identity-bound agreement signature.
- A client can send a rotation request or response only after it has observed the peer identity and that identity is not in `mismatch` state.
- A client signs outgoing rotation requests/responses with its local persisted E2E identity material. Incoming rotation messages are accepted only when the sender identity fingerprint matches the locally observed peer identity, the receiver identity fingerprint matches the local identity, and the agreement signature verifies against the pinned sender identity public material.
- Rotation request/response messages carry only public agreement material. Each side keeps its private agreement scalar locally, validates the identity-bound transcript, and derives the same session key from the shared transcript before marking the data plane `ready`.
- Missing pending agreement state, mismatched peer IDs, mismatched identity fingerprints, missing/tampered agreement signatures, invalid local private/public pairing, or malformed remote public material fail closed and do not install a session.
- The server validates shape and routing, then forwards only public agreement material. For remote Redis-present users it publishes an `e2e_control` event that contains the same public identity or signed agreement material and is delivered only to the online receiver instance. It does not cache identity keys, session keys, or private material.
- This is still a draft productization step using Qt primitives for testable authenticated agreement semantics. It is now signature-gated, cross-device-code gated, and production-required fail-closed at the client protocol boundary, but still needs a reviewed production cryptographic backend before it should be treated as an audited production suite.

## Current Cross-Device Trust Boundary

- Local E2E identity private material is persisted per local account under the app data directory, so a restart keeps the same advertised public-key fingerprint instead of breaking previously pinned peers.
- Each side computes the same short cross-device verification code from the local and peer identity fingerprints. The contact context menu can copy the code for comparison over a trusted channel, or accept an entered code to promote a pinned identity to `trusted`.
- Peer trust pins are persisted per local account as SHA-256 fingerprints plus verification state, verification code, and timestamps. The trust store does not contain peer public keys, local private agreement material, session keys, passwords, tokens, or server endpoints.
- A newly observed peer identity is automatically marked `trusted` only when it matches a persisted verified pin and the verification code still matches; unverified pins stay `pending-verification`, and conflicting fingerprints become `mismatch`.
- The contact context menu can clear a persisted trust pin and recover the peer to `unverified` without deleting the latest observed identity.
- The default data-plane policy requires a verified, trusted, non-mismatched peer identity before starting key agreement, accepting key agreement, or sending encrypted private messages. Stale sessions are not enough after trust recovery clears a pin.
- Corrupted local identity stores are regenerated with a fresh persisted identity, while malformed trust pins are ignored instead of being treated as trusted.

## Current History Metadata Boundary

- The local `chat_history` table is migrated in place with `encryption_state`, `e2e_key_id`, and `e2e_key_fingerprint` columns.
- Legacy rows with no encryption metadata are normalized to `plaintext`; new encrypted private-message rows are stored as `encrypted`, and valid envelopes that cannot decrypt are stored as `decrypt-failed`.
- History loading, date filtering, legacy text fallback, and export formatting now show explicit E2E state labels for encrypted or failed records while leaving plaintext rows visually unchanged.
- History metadata stores the key id and a short display fingerprint derived from the local session status when it matches the envelope key id. Raw session keys, private agreement material, peer public keys, passwords, tokens, and full fingerprints are not exported through this formatting path.
- This is metadata governance for local history visibility and auditability. It does not retroactively encrypt old plaintext history rows.

## Current File Payload Boundary

- Private file and image sends now use the same verified, trusted, non-mismatched peer identity and ready local E2E session as encrypted private text by default. Missing session, unverified identity, mismatch, or rotation-required state fails closed instead of silently sending private file payloads as plaintext.
- The sender encrypts the whole file payload into one E2E envelope, then sends the opaque ciphertext through the existing file chunk path. The server can validate and store only ciphertext size/hash and transfer metadata.
- Redis large-file object routing now preserves E2E file evidence without putting full ciphertext in Redis. The source instance writes only the ciphertext object and publishes a compact `large_file_offer` with E2E file key id, key fingerprint, plaintext size/hash, and an envelope header without `ciphertext`; the remote instance forwards chunks with that header, the receiver reconstructs the full envelope from collected ciphertext chunks, then authenticates and decrypts locally.
- `large_file_delivered` and `large_file_failed` events preserve the same E2E evidence fields so release/cleanup review can distinguish ciphertext routing hash from plaintext verification hash without logging private keys, session keys, plaintext payload, full peer public keys, or object-store credentials.
- The receiver collects the ciphertext chunks, authenticates the E2E envelope locally, decrypts the plaintext payload, and verifies the declared plaintext size and SHA-256 hash before surfacing the file message.
- Missing trust on an existing session, rotation-required sessions, invalid envelopes, authentication failure, plaintext size mismatch, or plaintext hash mismatch fail closed. Raw session keys, private agreement material, plaintext payloads, and full key material are not written into wire status or server logs.
- E2E file resume is intentionally conservative: interrupted encrypted private file sends are persisted with `recoveryMode=resend`, sanitized key id/fingerprint plus plaintext/wire size/hash evidence, and a fixed `e2e-file-resend-required` reason. The client refuses automatic resume queries for those records, keeps the state until the user resends or clears it, and the UI disables the resume action while explaining the resend requirement. Plaintext/public file recovery remains resumable. Group files, production crypto replacement, and richer resumable encrypted upload UX remain separate productization work. Protocol/operations tests that intentionally exercise legacy plaintext private-file routing must opt in with `QTNETWORKCHAT_E2E_ALLOW_PLAINTEXT_PRIVATE_FILE=1`; production defaults keep this path closed.

- Replace the linked `openssl-reviewed-adapter-v1` placeholder with reviewed production operations so `productionReady=true` can be reported only when key generation, agreement, signatures, payload encryption/decryption, protocol compatibility, and fail-closed tests all pass.
- Replace harness-blocked placeholders with real reviewed operation executions, then flip `productionAcceptance.accepted=true` only after every production operation implementation slot has a reviewed implementation, compatible vector evidence, no sensitive material export, passing harness status, passing execution-plan status, callable invocation contracts, reviewed operation slots, callable dispatch bindings, callable manifest ABI/fixture evidence, sanitized execution result evidence, provider C ABI header match, provider table structural validation, runtime provider table registration, provider operation preflight, provider call frame construction, provider invocation dry-run, provider table binding probe, bound provider table symbols, and passing dispatch under production-required mode.
- Extend tests so `selectedBackendId` and `productionReady=true` become possible only after production key generation, public-key derivation, signing, verification, session derivation, encryption, decryption, and client identity announcement all pass under production-required mode.
- Replace the current destructive local migration execution with a true rotation path that creates production identity material, rebinds peer trust pins, and rotates active sessions onto the linked production backend after reviewed operations exist.
- Add migration checks for older identity/pin store schemas and richer operator/user recovery prompts.
- Extend encrypted file recovery beyond the current resend-on-interruption policy with resumable envelope/object evidence once the production crypto backend and key-rotation persistence model are ready.
