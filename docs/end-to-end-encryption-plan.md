# End-to-End Encryption Hardening Plan

QtNetworkChat currently treats the server as a transparent carrier for private-message E2E envelopes, identity announcements, and session rotation control messages. The client keeps the trust decision local: peer identity public keys are observed from online announcements, displayed as SHA-256 fingerprints, and verified with a short cross-device code before the default encrypted data plane is allowed. Authenticated session setup now requires identity-signed request/response transcripts and derives local session keys without sending the raw session key over the wire. Redis-backed multi-instance deployments also route E2E identity announcements and signed rotation control messages as small control-plane events; session keys, private identity material, and full file ciphertext are still not cached in Redis.

## Current Authenticated Agreement Boundary

- The E2E cryptographic surface now has an explicit backend contract. CMake generates a sanitized `qtnetworkchat_e2e_crypto_config.h` with compiled backend id, requested production backend, production adapter id, production request/availability flags, adapter linked flag, required operation list, provider API header path, provider table ABI, required provider symbols, provider table binding flag, and reason strings. The public `qtnetworkchat_e2e_provider_api.h` fixes the reviewed adapter C ABI: table ABI, operation contract version, operation enum, material policy enum, input/output structs, operation function pointer, and eight-symbol provider table. Runtime status exposes `compiledBackendId`, `requestedBackendId`, `selectedBackendId`, `selectionSource`, `registeredBackends`, `selectedProviderReadiness`, `selectedProviderCompatibility`, `productionAdapterLinked`, `productionReady`, `productionRequiredOperations`, `available`, `productionRequired`, `unavailableReason`, and an operator action. The same status publishes a sanitized per-operation matrix for session-key generation, identity-key generation, public-key derivation, agreement signing, signature verification, session derivation, payload encryption, and payload decryption; every public E2E primitive is gated through the shared adapter execution context and provider dispatch contract. Linked reviewed OpenSSL builds can now select `openssl-reviewed-adapter-v1`, report `productionReady=true`, dispatch the public API through the provider, and promote sanitized provider invocation probe evidence through reviewed handoff/data-plane/public primitive gates into `productionAcceptance.accepted=true` without exposing raw keys, private identity material, session secrets, plaintext payloads, or ciphertext bytes in status evidence.
- `QTNETWORKCHAT_E2E_ENABLE_PRODUCTION_CRYPTO=ON` plus `QTNETWORKCHAT_E2E_PRODUCTION_CRYPTO_BACKEND=openssl` remains a CMake probe path unless the adapter is explicitly linked. `QTNETWORKCHAT_E2E_LINK_PRODUCTION_ADAPTER=ON` links the OpenSSL provider table when OpenSSL is found; that path exposes `productionAdapterRequested=true`, `productionAdapterLinked=true`, `productionAdapterReason=production-adapter-linked-reviewed-operations`, `productionProviderTable.buildProbeReason=production-provider-table-reviewed-operations-bound`, and reviewed implementations for all eight callbacks. The runtime self-test verifies key generation, public derivation, Ed25519 signing/verification, HKDF session derivation, AES-GCM encryption/decryption, and signature/ciphertext tamper rejection before marking the adapter `production-dispatch-ready`.
- `e2eProbeProductionCryptoProviderInvocationExecution()` is an explicit test probe that can invoke a registered provider table and records only status classes, vector result class, failure class, consistency class, sizes, and material-export proof; linked builds also use this sanitized result as the default evidence source for reviewed candidate, handoff, stub, callable bridge/interface, runtime preflight, arming, execution acceptance, data-plane bridge, public primitive execution, and production crypto acceptance. `e2eProbeProductionCryptoProviderRoundTripExecution()` executes identity generation, public derivation, Ed25519 signing, signature verification, HKDF session derivation, AES-GCM payload encryption/decryption, and tamper rejection as one internal vector chain while exporting only status, sizes, booleans, and sanitized failure classes. `e2eProbeProductionCryptoProviderPublicPrimitiveExecution()` adds the public-primitive-shaped version of that chain. Production rotation now has a linked-provider local rebind execution layer; full peer trust/session rotation remains separate work.
- Operators can set `QTNETWORKCHAT_E2E_REQUIRE_PRODUCTION_CRYPTO=1` to fail closed when the current build has only the draft backend, or set `QTNETWORKCHAT_E2E_CRYPTO_BACKEND=production` / `openssl` to explicitly request the production adapter. If the adapter is not linked, operations fail with `production-crypto-backend-unavailable`; if it is linked and self-tested, operations use the OpenSSL provider and do not silently fall back to draft. Unknown backend ids are sanitized, every operation reports `unsupported-crypto-backend`, and there is no silent fallback to draft when a production adapter was requested.
- Local identity stores, trust pins, and in-memory sessions now carry backend migration evidence. Existing draft identity files remain inspectable under a production backend request, including their stored public-key fingerprint and `backendId=draft-qt-hmac-stream-v1`, but status marks `backendMigrationRequired=true`, disables agreement signing, and blocks identity announcements, encrypted sends, and rotation. Trust pins and sessions expose the same draft backend id plus blocked reason so operators can distinguish "adapter unavailable" from "stored draft material needs migration" without dumping private keys, raw session keys, or peer public keys.
- Migration recovery is explicit and evidence-backed for local draft E2E state. `planE2EBackendMigration` reports sanitized counts, affected peers, backend ids, blocked reasons, and short fingerprint summaries without private keys, raw session keys, peer public keys, local paths, or full fingerprints. `planE2EProductionRotationDryRun` adds a non-destructive production rotation readiness view over the same local state: it reports provider readiness/compatibility gates, affected peer pins and sessions, and whether in-place rotation can proceed, while proving it will not clear identity stores, trust pins, active sessions, or pending agreements during dry-run. Until the provider is production-ready, the dry-run release gate remains `production-crypto-provider-not-ready`. The same dry-run and `executeE2EProductionRotation` evidence now include the shared `productionAcceptance` gate, `productionOperationExecutionPlan`, `productionOperationInvocation`, `productionOperationSlots`, `productionOperationDispatchBindings`, `productionOperationExecutionResult`, `productionProviderTableRegistration`, `productionProviderOperationPreflight`, `productionProviderInvocationDryRun`, `productionProviderExecutionDecision`, `productionProviderCallbackHarness`, `productionProviderVectorSelfTest`, `productionProviderExecutionSlotBinding`, and a seven-stage rotation manifest for production identity generation, public derivation, agreement sign/verify, session derivation, payload encrypt, and payload decrypt, with each stage tied to the selected provider operation matrix and compatibility gate. When `canRotateInPlace=true`, production acceptance is satisfied, and every execution/preflight/dispatch gate is ready, `executeE2EProductionRotation` now calls the linked provider to generate fresh production local identity material, persists the production backend id, clears draft sessions and pending agreements, resets peer pins for re-verification, and returns sanitized local rebind evidence with counts and short fingerprint summaries only. It still does not claim full peer/session rotation: after execution the client must announce the production identity, peers must re-check verification codes, trust pins must be rebound, and new signed production session agreements must be derived before encrypted private text or files can resume. `executeE2EBackendMigration` remains the destructive compatibility recovery path for clearing draft local state when production rotation cannot proceed.
- `E2EKeyAgreement` now carries both `senderIdentityFingerprintSha256` and `receiverIdentityFingerprintSha256` in addition to the rotation public key fingerprint and a draft identity-bound agreement signature.
- A client can send a rotation request or response only after it has observed the peer identity and that identity is not in `mismatch` state.
- A client signs outgoing rotation requests/responses with its local persisted E2E identity material. Incoming rotation messages are accepted only when the sender identity fingerprint matches the locally observed peer identity, the receiver identity fingerprint matches the local identity, and the agreement signature verifies against the pinned sender identity public material.
- Rotation request/response messages carry only public agreement material. Each side keeps its private agreement scalar locally, validates the identity-bound transcript, and derives the same session key from the shared transcript before marking the data plane `ready`.
- Missing pending agreement state, mismatched peer IDs, mismatched identity fingerprints, missing/tampered agreement signatures, invalid local private/public pairing, or malformed remote public material fail closed and do not install a session.
- The server validates shape and routing, then forwards only public agreement material. For remote Redis-present users it publishes an `e2e_control` event that contains the same public identity or signed agreement material and is delivered only to the online receiver instance. It does not cache identity keys, session keys, or private material.
- This is still a draft productization step using Qt primitives for testable authenticated agreement semantics. It is now signature-gated, cross-device-code gated, and production-required fail-closed at the client protocol boundary, but still needs a reviewed production cryptographic backend before it should be treated as an audited production suite.

## Current Cross-Device Trust Boundary

- Local E2E identity private material is persisted per local account under the app data directory, so a restart keeps the same advertised public-key fingerprint instead of breaking previously pinned peers.
- Each side computes the same short cross-device verification code from the local and peer identity fingerprints. The contact context menu can copy the code for comparison over a trusted channel, or accept an entered code to promote a pinned identity to `trusted`.
- Peer trust pins are persisted per local account as SHA-256 fingerprints plus verification state, verification code, and timestamps. The trust store does not contain peer public keys, local private agreement material, session keys, passwords, tokens, or server endpoints.
- A newly observed peer identity is automatically marked `trusted` only when it matches a persisted verified pin and the verification code still matches; unverified pins stay `pending-verification`, and conflicting fingerprints become `mismatch`.
- The contact context menu can clear a persisted trust pin and recover the peer to `unverified` without deleting the latest observed identity.
- The default data-plane policy requires a verified, trusted, non-mismatched peer identity before starting key agreement, accepting key agreement, or sending encrypted private messages. Stale sessions are not enough after trust recovery clears a pin.
- Corrupted local identity stores are regenerated with a fresh persisted identity, while malformed trust pins are ignored instead of being treated as trusted.

## Current History Metadata Boundary

- The local `chat_history` table is migrated in place with `encryption_state`, `e2e_key_id`, and `e2e_key_fingerprint` columns.
- Legacy rows with no encryption metadata are normalized to `plaintext`; new encrypted private-message rows are stored as `encrypted`, and valid envelopes that cannot decrypt are stored as `decrypt-failed`.
- History loading, date filtering, legacy text fallback, and export formatting now show explicit E2E state labels for encrypted or failed records while leaving plaintext rows visually unchanged.
- History metadata stores the key id and a short display fingerprint derived from the local session status when it matches the envelope key id. Raw session keys, private agreement material, peer public keys, passwords, tokens, and full fingerprints are not exported through this formatting path.
- This is metadata governance for local history visibility and auditability. It does not retroactively encrypt old plaintext history rows.

## Current File Payload Boundary

- Private file and image sends now use the same verified, trusted, non-mismatched peer identity and ready local E2E session as encrypted private text by default. Missing session, unverified identity, mismatch, or rotation-required state fails closed instead of silently sending private file payloads as plaintext.
- The sender encrypts the whole file payload into one E2E envelope, then sends the opaque ciphertext through the existing file chunk path. The server can validate and store only ciphertext size/hash and transfer metadata.
- Redis large-file object routing now preserves E2E file evidence without putting full ciphertext in Redis. The source instance writes only the ciphertext object and publishes a compact `large_file_offer` with E2E file key id, key fingerprint, plaintext size/hash, and an envelope header without `ciphertext`; the remote instance forwards chunks with that header, the receiver reconstructs the full envelope from collected ciphertext chunks, then authenticates and decrypts locally.
- `large_file_delivered` and `large_file_failed` events preserve the same E2E evidence fields so release/cleanup review can distinguish ciphertext routing hash from plaintext verification hash without logging private keys, session keys, plaintext payload, full peer public keys, or object-store credentials.
- The receiver collects the ciphertext chunks, authenticates the E2E envelope locally, decrypts the plaintext payload, and verifies the declared plaintext size and SHA-256 hash before surfacing the file message.
- Missing trust on an existing session, rotation-required sessions, invalid envelopes, authentication failure, plaintext size mismatch, or plaintext hash mismatch fail closed. Raw session keys, private agreement material, plaintext payloads, and full key material are not written into wire status or server logs.
- E2E file resume is intentionally conservative: interrupted encrypted private file sends are persisted with `recoveryMode=resend`, sanitized key id/fingerprint plus plaintext/wire size/hash evidence, and a fixed `e2e-file-resend-required` reason. The client refuses automatic resume queries for those records, keeps the state until the user resends or clears it, and the UI disables the resume action while explaining the resend requirement. Plaintext/public file recovery remains resumable. Group files, production crypto replacement, and richer resumable encrypted upload UX remain separate productization work. Protocol/operations tests that intentionally exercise legacy plaintext private-file routing must opt in with `QTNETWORKCHAT_E2E_ALLOW_PLAINTEXT_PRIVATE_FILE=1`; production defaults keep this path closed.

## Remaining Work

- Replace the draft agreement/signature primitive in full client flows with the reviewed production backend and durable signed identity keys.
- Extend linked-provider production crypto acceptance into production-required client behavior: identity announcement, peer pinning, session rotation, encrypted text, encrypted file payloads, mismatch-free output-shape evidence, and no-sensitive-export proof under production-required mode.
- Extend tests from provider/runtime coverage into full client flows so production identity announcement, peer pinning, session rotation, encrypted text, and encrypted file payloads all pass under production-required mode.
- Extend the local production identity rebind into a true peer rotation path that rebinds trust pins and rotates active sessions onto the linked production backend.
- Add migration checks for older identity/pin store schemas and richer operator/user recovery prompts.
- Extend encrypted file recovery beyond the current resend-on-interruption policy with resumable envelope/object evidence once the production crypto backend and key-rotation persistence model are ready.
